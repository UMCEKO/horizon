# X3: real host Text stack measurements (partial)

## Base and scope

Measured after plain merges of integration head `884550f6dc` and X2 head
`4d55c46f9c8d09ecfe00d7dabad26bbba85a3246`. This is a measurement deliverable,
**not completion of X3**. No production thread stack settings are changed.

The binary compiles the production `api_values/text_boundary.rs` directly through
this crate, not a copy or a synthetic API tree constructor. It loads the player's
prepared vanilla language data privately, builds a 512-node component using each
recursive Text relation, and calls the real engine `component::to_text` with a
resolver backed by that language data. It then captures the real engine Text,
clones and drops the API tree, converts back through the actual boundary, clones
and drops the restored engine Text, and drops every remaining tree. It does not
forget recursive values. The nested topology is adversarial fixture data, not a
claim that vanilla ships a particular 512-deep message. No vanilla bytes are
included in this directory or the report.

`stack_need.py` bisects in fresh child processes, at 4 KiB resolution, accepting
only successful completion or SIGABRT with Rust's stack-overflow diagnostic. Each
boundary is repeated three times on both sides. Each attempt requests its own
thread stack explicitly. Core dumps are disabled. The script is Unix-only.

## Results

Linux x86_64, Rust 1.99.1, `dev` profile (unoptimized), system allocator. These are
requested thread-stack sizes, not portable exact usable-byte counts. ASLR, guard
pages, compiler versions, profiles and surrounding game frames affect the result.
The JSON beside this file records the actual final bisection output. An earlier
build of the same workload varied by one 4 KiB step; do not treat byte values as
cross-machine constants.

| Relation | Last overflow bytes | First passing bytes |
| --- | ---: | ---: |
| extra | 1,388,544 | 1,392,640 |
| translation argument | 2,056,192 | 2,060,288 |
| hover text | 1,957,888 | 1,961,984 |
| selector separator | 561,152 | 565,248 |
| atlas fallback | 1,601,536 | 1,605,632 |
| entity hover name | 1,884,160 | 1,888,256 |
| NBT separator | 561,152 | 565,248 |
| player fallback | 1,601,536 | 1,605,632 |

All eight relations also completed separately at exactly 2 MiB and 8 MiB.
The worst passing observation is 2,060,288 bytes. For **this Text-only workload**,
`max(4 MiB, ceil(2 * need / MiB) * MiB)` yields 4 MiB, a 2.036x ratio.
It does **not** establish the requested margin for stack/snapshot hooks or the
full server tick frame, and no constant was installed on that basis.

A measurement-harness mutant deleting `.stack_size(bytes)` aborted (exit 134,
stack overflow) with `RUST_MIN_STACK=65536` while requesting 8 MiB on the command
line. The restored binary completed (exit 0) with the same environment and input.
This kills an implicit-stack mutant in the measurement constructor only; it is
not the required per-production-builder regression.

## Thread audit

`thread-inventory.md` lists builder and unscoped spawn sites in client, render,
core, input and horizon-threads, including examples and tests. It is a source
inventory, not a completed call-graph proof of every hook-owning worker. Scope
spawns also exist in `game.rs` loading, `game/world/packs`, world loading,
`mod_content`, LAN connection packet encoding, render pack preparation, HUD,
`par.rs`, and saves. None of the following production builder families supplies
an explicit stack in this dependency head:

- Integrated server: `game/world/integrated.rs:488`; the launch-test constructor
  at 1276 likewise has no size. This is an actual Game owner, with lifecycle and
  tick callbacks.
- Network: `net.rs:241` (`horizon-net`).
- LAN: `lan/mod.rs:704,736,958` (accept, local connection, remote connection),
  `lan/io_pool.rs:228` (I/O reactor), `lan/chunks.rs:500` (chunk worker).
  LAN Hub has restricted-context Text formatting hooks; do not infer that every
  LAN thread owns a Game or that raw socket I/O itself performs API conversion.
- World initialization/preload: `game/world/world_loading.rs:319,379,454,516`,
  server data preload `game/network/lan/mod.rs:394`, and game loading builders.
- Worldgen/meshing streaming workers use `horizon_threads::jobs::Pool`, whose
  worker constructor is `crates/horizon-threads/src/jobs.rs:223`, rather than a
  Rayon pool. No Rayon pool constructor was found in the audited client sources.

Renderer, audio, skin/asset download, recorder, logging, discovery and CLI/test
workers are separately visible in the inventory; they should not all get larger
stacks merely because they use threads. Their actual callback reachability still
needs classification. Hook dispatch and resource conversion during load need
particular attention before excluding load workers.

The initial game thread is not spawned by a Rust Builder. `horizon-client/build.rs`
sets Windows `/STACK:8388608` or GNU `--stack,8388608`. There is no corresponding
explicit Linux/macOS setup in this file. The measurement shell's Linux limit was
8 MiB; that is not a portable launch guarantee. Moving winit's event loop onto a
new worker is not an acceptable blanket fix for macOS's main-thread requirement.

## Remaining work / dependency limit

X2's own README explicitly records unfinished depth refusal and recursive final
engine span construction. Its conversion trait still returns `Infallible` and
accepts arbitrary depth. This measurement does not make that boundary bounded or
safe; it deliberately measures the real current code, including its recursive
engine builder. X3 must be rerun when X2 changes those frames.

The worst-case stack/snapshot hook workload has **not been measured**. The
measurement binary does not link Game, install Parts, or dispatch a subscribed
snapshot hook. Consequently the global required maximum is unknown. A shared
production constant, all affected builder changes, main-thread platform handling,
and per-family stack-size mutants are **not implemented**. Installing a constant
and claiming the task's margin now would overstate this evidence. These are
remaining implementation/proof work, not waived requirements.

No main-versus-head tick timing or allocation measurement was done; this change
only adds a developer probe and has no game hot-path effect. No WIT, API catalog
or host manifest input was changed by X3. Workspace checks, clippy and boundary
CI gates were not run locally; room rules leave those checks to CI.

## Reproduction

```sh
cargo build --manifest-path tools/refactors/api-pr3/text-boundary-tests/Cargo.toml --bin stack-need
python3 tools/refactors/api-pr3/text-boundary-tests/stack_need.py \
  "$CARGO_TARGET_DIR/debug/stack-need" "$PRIVATE_PREPARED_RESOURCES/assets/minecraft/lang/en_us.json"
cargo test --manifest-path tools/refactors/api-pr3/text-boundary-tests/Cargo.toml iterative_tests::
```
